# คำถามถึงทีม Player — ข้อมูลที่ยังขาดสำหรับระบบแปลงไฟล์อัตโนมัติ

ถึง: ทีม AdsManager Android / Windows
จาก: ทีม Thunder One (Media Workspace)
วันที่: 9 กันยายน 2026
อ้างอิง: `VIDEO_CODEC_SUPPORT.md` (9 กันยายน 2026)

---

## บริบท

เรากำลังทำระบบที่**แปลงไฟล์วิดีโอให้อัตโนมัติตอนอัปโหลด** ให้ได้รูปแบบกลางที่เอกสารของคุณระบุไว้:

> MP4 + H.264 Constrained Baseline + yuv420p (8-bit) + AAC-LC

เอกสารของคุณ**เพียงพอ**ที่จะกำหนดรูปแบบปลายทางและกติกาบล็อกฝั่ง Android (profile High = บล็อก, HEVC = บล็อก) เราเริ่มงานได้ทันทีจากตรงนี้

แต่เอกสารระบุเองว่า *"ต้องอยู่ในขีดจำกัด decoder ของเครื่อง"* โดย**ไม่ได้ให้ตัวเลข** เราจึงต้องตั้งค่าบางอย่างเป็น**สมมติฐาน** ไปก่อน

**เอกสารนี้มี 2 ส่วน:**
1. สมมติฐานที่เราตั้งไว้แล้ว — ขอให้ยืนยันหรือแก้
2. คำถามที่เรายังตอบเองไม่ได้

> เราไม่รอคำตอบก่อนเริ่มงาน สมมติฐานข้างล่างถูกบันทึกไว้ใน ADR ของเราแล้วว่า "ยังไม่ได้รับการยืนยัน" เมื่อได้คำตอบจริงเราจะปรับค่าแล้วแปลงไฟล์ใหม่ (เราเก็บไฟล์ต้นฉบับไว้เพื่อการนี้)

---

## ส่วนที่ 1 — สมมติฐานที่เราตั้งไว้ ขอให้ยืนยัน

| # | สมมติฐาน | ค่าที่เราตั้ง | ถ้าผิดจะเกิดอะไร |
|---|---|---|---|
| A1 | H.264 **Level** สูงสุดที่ตู้รับได้ | `4.0` | ตั้งสูงไป = ตู้ถอดรหัสไม่ไหว, ตั้งต่ำไป = คุณภาพตกโดยไม่จำเป็น |
| A2 | **ความละเอียด**สูงสุด | `1920×1080` | ไฟล์ 4K ที่อัปโหลดเข้ามาจะถูกย่อลง |
| A3 | **Frame rate** สูงสุด | `30 fps` | วิดีโอ 60 fps จะถูกลดเฟรม |
| A4 | **Bitrate** เป้าหมาย | `6 Mbps` @1080p | สูงไป = ตู้กระตุก / ดาวน์โหลดนาน, ต่ำไป = ภาพแตก |
| A5 | **Pixel format** | `yuv420p` 8-bit | (ยืนยันแล้วในเอกสารของคุณ) |
| A6 | **เสียง** | AAC-LC 128 kbps stereo 48 kHz | ดู Q4 |

**คำขอ:** ถ้าค่าไหนผิด รบกวนระบุค่าที่ถูกต้อง ถ้าไม่แน่ใจ รบกวนบอกว่า "ไม่แน่ใจ" — เราต้องการทราบว่าอะไรคือข้อเท็จจริงและอะไรคือการเดา มากกว่าต้องการตัวเลขที่ดูดี

## ส่วนที่ 2 — คำถาม

### Q1 — H.264 Level สูงสุด และรุ่นตู้อ้างอิง

Level เป็นตัวกำหนดเพดาน macroblock/วินาที และ bitrate ที่ decoder รับได้ เอกสารไม่ได้ระบุ

- ตู้ Android รุ่นที่ใช้งานจริงคือรุ่นอะไร (ยี่ห้อ/SoC/Android version)
- ถ้ามีหลายรุ่น รุ่นที่**อ่อนที่สุด**คือรุ่นไหน — เราจะตั้งค่าตามรุ่นนั้น
- Windows mini PC ที่ใช้ mpv สเปคประมาณไหน

### Q2 — เพดานความละเอียดและ frame rate

- 1080p30 เพียงพอสำหรับงานทั้งหมดหรือไม่
- มีจอที่ต้องการมากกว่า 1080p หรือไม่ (เช่นจอ LED แนวตั้งความละเอียดสูง)
- ถ้ามีวิดีโอ 60 fps ตู้เล่นได้ลื่นหรือไม่

### Q3 — จำนวน decoder พร้อมกัน (multi-zone) ⚠️ สำคัญที่สุด

เอกสารระบุว่า *"multi-zone, preload และ transition อาจใช้ทรัพยากรมากกว่าการเล่นวิดีโอเดียว"* แต่ไม่ได้ให้ตัวเลข

- ตู้หนึ่งเครื่อง**ถอดรหัสวิดีโอพร้อมกันได้กี่ตัว** ที่ 1080p30
- ตอน preload วิดีโอถัดไประหว่างที่วิดีโอปัจจุบันยังเล่นอยู่ นับเป็น 2 decoder หรือไม่
- **ถ้าตู้รับได้แค่ 2 ตัวพร้อมกัน เราอาจต้องลด bitrate หรือความละเอียดลงสำหรับงานหลายโซนโดยเฉพาะ** ซึ่งเปลี่ยนวิธีออกแบบระบบแปลงไฟล์ของเรา (จากค่าเดียวใช้ทุกงาน เป็นค่าที่ขึ้นกับ Layout)

### Q4 — เสียงถูกใช้งานจริงหรือไม่

ฝั่งเราตั้งค่า mute ได้รายโซน

- งานจริงมี Publication ที่เปิดเสียงหรือไม่
- ถ้าไม่มีเลย เราจะ**ตัด audio track ทิ้ง** ซึ่งลดขนาดไฟล์และลดภาระ decoder
- ถ้ามี AAC-LC 128 kbps stereo 48 kHz เพียงพอหรือไม่

### Q5 — H.264 Main Profile เล่นได้จริงหรือไม่

เอกสารระบุว่า *"แอพไม่บล็อก แต่ยังต้องทดสอบ"*

- มีการทดสอบ Main Profile กับตู้จริงแล้วหรือยัง ผลเป็นอย่างไร
- **สถานะปัจจุบันของเรา: ADR 0070 รับ Main เป็น `ready` พร้อม `probe_verdict.code = unverified_preset`** เพราะ Player ไม่ได้บล็อก profile นี้ แต่ยังไม่มีหลักฐานรับรอง; เมื่อ ADR 0071 พร้อม ระบบจะให้กลุ่มนี้อยู่ต้นคิวแปลงแทนการกักไฟล์ทันที
- ถ้ายืนยันได้ว่า Main เล่นได้จริง เราจะเลิกแปลง Main ซึ่งช่วยรักษาคุณภาพไฟล์ไว้ได้

### Q6 — รูปภาพ (สำคัญ แต่เอกสารไม่ได้พูดถึงเลย) ⚠️

ระบบเรารับไฟล์ภาพ **PNG, JPG, WebP** และส่งไปตู้ แต่เอกสารของคุณไม่ได้กล่าวถึงรูปภาพแม้แต่บรรทัดเดียว

- **Android app แสดง WebP ได้หรือไม่**
- **mpv บน Windows แสดง WebP ได้หรือไม่**
- PNG ที่มีช่อง alpha (โปร่งใส) แสดงผลอย่างไร
- มีเพดานความละเอียดของภาพหรือไม่ (เช่นภาพ 8000×8000 px)
- มีเพดานขนาดไฟล์ภาพหรือไม่

> เหตุผลที่ถาม: นี่คือปัญหาประเภทเดียวกับวิดีโอ — เรารับไฟล์เข้าระบบโดยไม่มีหลักฐานว่าตู้แสดงผลได้ ถ้า WebP ใช้ไม่ได้ เราจะแปลงเป็น JPG ให้ ซึ่งเป็นงานเล็กมาก แต่เราต้องรู้ก่อน

### Q7 — H.264 profile ขั้นสูงอื่นๆ

เอกสารระบุว่าโค้ดไม่ได้บล็อกครอบคลุมทุก profile

- **High 10 / High 4:2:2 / High 4:4:4** — แอพควรบล็อกด้วยหรือไม่
- ถ้าใช่ ฝั่งเราจะกันตั้งแต่ต้นทางให้ ไม่มีทางหลุดไปถึงตู้

### Q8 — Container ที่ไม่ใช่ MP4

- ถ้าเป็นไฟล์ `.mkv` หรือ `.mov` ที่ข้างในเป็น H.264 Constrained Baseline ตู้เล่นได้หรือไม่
- (ฝั่งเรารับเฉพาะ `.mp4` อยู่แล้ว คำถามนี้ไว้ยืนยันว่าไม่ต้องเปิดรับเพิ่ม)

### Q9 — ตู้มีทางแจ้งกลับมาหรือไม่ว่าเล่นไม่ได้

เอกสารระบุว่าเมื่อบล็อก แอพส่งเหตุผล `H264_HIGH_PROFILE` / `HEVC_UNSUPPORTED` ออกมา

- เหตุผลนี้**ส่งกลับมาที่ backend หรือไม่** หรืออยู่แค่ใน log ของเครื่อง
- ถ้ายังไม่ส่ง **เป็นไปได้ไหมที่จะส่ง** — เราจะเอามาแสดงให้ผู้ใช้เห็นทันทีว่าสื่อชิ้นไหนถูกปฏิเสธและเพราะอะไร
- ปัจจุบันผู้ใช้ฝั่งเราเห็นสถานะว่าสื่อ "พร้อมใช้งาน" ทั้งที่ตู้ปฏิเสธไปแล้ว — **นี่คือช่องว่างที่ทำให้เคส "อัปโหลด 3 เล่นได้ 2" ไม่มีใครสังเกตเห็น**

## สิ่งที่ฝั่งเราจะทำตาม ADR 0069–0071

1. ตรวจไฟล์ทุกไฟล์ที่อัปโหลดเข้ามา อ่าน codec/profile จริงจากตัวไฟล์ ไม่เชื่อนามสกุล
2. กัก High Profile / HEVC / ไฟล์ที่อ่าน profile ไม่ได้เป็น `failed`; รับ Main เป็น `ready` พร้อม
   `unverified_preset` และส่งเข้า full-assessment queue เมื่อ ADR 0071 พร้อม การประเมินไม่เปลี่ยน
   `status`: เฉพาะ Asset ที่ตู้ปฏิเสธจริงจะเป็น `processing` เมื่อเริ่ม encode ส่วน Main และ Asset ที่
   ตกเพียง provisional ceiling จะคง `ready`; Vercel จะแปลงต่อเฉพาะ Asset ที่อยู่ใน
   automatic-conversion envelope และถ้า Asset แบบ provisional ถูกใช้อยู่ใน Active Publication
   ระบบจะยังไม่สลับไฟล์กลางการฉาย แต่รอ Operations ติดตั้ง rendition ใน change window
3. ตรวจย้อนหลังสื่อทั้งหมดที่มีอยู่ในระบบ แล้วติดธงตัวที่ตู้น่าจะเล่นไม่ได้
4. เก็บไฟล์ต้นฉบับไว้ เพื่อแปลงใหม่ได้เมื่อ measurement campaign ให้ตัวเลขจริง

**ข้อ 3 จะบอกเราได้ว่าตอนนี้มีสื่อเสียอยู่ในระบบกี่ชิ้น — เราจะส่งตัวเลขนั้นกลับไปให้ทีมคุณด้วย**
