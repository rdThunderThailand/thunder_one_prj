## วัตถุประสงค์ของ flow นี้

**เพิ่มพนักงานใหม่ = สร้างบัญชีจริงใน Core (Membership/Invitation) + เริ่มติดตาม Onboarding ได้ทันที**
ไม่ใช่แบบฟอร์มเก็บข้อมูลบุคคลากรแบบครบถ้วน (Full HR Record) ตั้งแต่วันแรก — ความแตกต่างนี้สำคัญ
เพราะกำหนดว่า field ไหน "จำเป็นต้องมี" กับ field ไหน "ดีถ้ามี แต่รอทีหลังได้"

## หลักการตัดสินใจ (ใช้กับทุก field)

ถามทีละ field 3 ข้อ:

1. **จำเป็นต่อการสร้างบัญชีจริง หรือกฎหมาย/นโยบายบังคับต้องเก็บตอน intake หรือไม่?** (เช่น
   เลขบัตรประชาชนใช้ทำสัญญาจ้าง/ยื่นภาษี แม้ Core ยังไม่มี column ก็ควรเก็บไว้)
2. **มี Core รองรับจริงแล้ว หรือมีแผนจะรองรับในเร็วๆ นี้หรือไม่?** (ดูจาก
   `add-employee-field-requirements.md`'s ข้อเสนอลำดับความสำคัญ)
3. **การเก็บไว้ตอนนี้ทั้งที่ยังไม่มีที่เก็บจริง เสี่ยงทำให้ HR เข้าใจผิดว่า "บันทึกแล้ว" หรือไม่?**
   (เช่น ผู้บังคับบัญชาที่เลือกในฟอร์ม — ปัจจุบันไม่ได้ถูกบันทึกที่ไหนเลย)

จากนั้นจัดแต่ละ field ลง 1 ใน 5 กลุ่ม:

| กลุ่ม | ความหมาย | การกระทำ |
|---|---|---|
| **A. Core จริง** | มี Core รองรับแล้ววันนี้ | คงไว้ตามเดิม |
| **B. จำเป็นตามกฎหมาย/นโยบาย แต่ Core ยังไม่รองรับ** | ต้องเก็บตอน intake แน่นอน | คงไว้ในฟอร์ม + เร่งให้ Core ทำ column จริง (priority สูงสุด) |
| **C. มีประโยชน์ชัดเจน รอ Core** | ช่วยจัดหมวดหมู่/รายงานได้จริง | คงไว้ + ผลักดัน Core ทำ แต่ไม่ใช่ blocker ของ intake |
| **D. ข้อมูลอ่อนไหว/ควรแยกสิทธิ์** | ไม่เกี่ยวกับ "สร้างบัญชี" โดยตรง เป็นข้อมูล compensation | พิจารณาแยกออกจาก flow นี้ ไปเป็นขั้นตอน/หน้าที่จำกัดสิทธิ์ผู้เข้าถึง |
| **E. ไม่มีที่เก็บจริง และคุณค่าไม่ชัด** | ไม่ตอบวัตถุประสงค์ข้อ 1 ของ flow นี้ | ตัดออกจาก UI จนกว่าจะมีเหตุผล/ที่เก็บจริง |

## จัดหมวดหมู่ field ทั้งหมด

### Step 1 — ข้อมูลส่วนบุคคล

| Field | กลุ่ม | เหตุผล |
|---|---|---|
| อีเมล | A | ส่งเข้า Core จริงแล้ว (`email`) |
| ชื่อ-นามสกุล (ไทย) | B | ใช้แสดงผล/ทำสัญญา แม้ Core `POST /members` ยังไม่รับ — แต่ `public.users` มี `first_name`/`last_name` อยู่แล้ว (ตาม Core's response doc) เป็นไปได้สูงว่าจะ map ได้เลย ไม่ต้องรอ column ใหม่ |
| เลขบัตรประชาชน | B | ใช้ทำสัญญาจ้าง/เอกสารราชการ — **ต้องแก้ bug ก่อน**: ตอนนี้ mark required ใน markup แต่ปุ่ม "ถัดไป" ไม่บังคับจริง ต้องเลือกทางใดทางหนึ่ง ไม่ปล่อยครึ่งๆ กลางๆ |
| วันเกิด, เพศ, สัญชาติ | B | ใช้กรอกแบบฟอร์มราชการ/ประกันสังคม — เก็บไว้แต่ต้น มีประโยชน์กว่าไปตามทีหลัง |
| ชื่อ-นามสกุล (อังกฤษ) | C | ใช้ทำบัตรพนักงาน/เอกสารต่างประเทศ มีประโยชน์แต่ไม่เร่งด่วน |
| เชื้อชาติ, เบอร์โทรศัพท์, ที่อยู่ | C | มีประโยชน์ระดับ HR record ทั่วไป ไม่ block การสร้างบัญชี |
| เลขหนังสือเดินทาง (ถ้ามี) | C | ใช้เฉพาะพนักงานต่างชาติ — เก็บแบบ optional ต่อไปเหมาะสมอยู่แล้ว |
| หมายเหตุ (ข้อมูลเพิ่มเติม) | C | free-text เสริม เก็บไว้ได้ ไม่กระทบ flow |
| รูปภาพพนักงาน (photo upload) | E | **ตอนนี้เป็น UI หลอก** (กดไม่ได้จริง) — UI ที่กดไม่ได้แย่กว่าไม่มี UI เลย: ตัดออกจนกว่าจะต่อ file storage จริง หรือถ้าจะเก็บไว้ ต้องมี timeline ทำจริงชัดเจน |

### Step 2 — ข้อมูลการจ้างงานและตำแหน่ง

| Field | กลุ่ม | เหตุผล |
|---|---|---|
| ตำแหน่งงาน (job_title), หน่วยงาน (default_department_id), Role (role_code) | A | ส่งเข้า Core จริงแล้ว |
| วันที่เริ่มงาน (start_date) | A | ส่งเข้า Core จริงแล้ว — **แนะนำเปลี่ยนให้ required** เพราะเป็นตัวกำหนดวันเริ่ม Onboarding ทั้งกระบวนการ ปล่อยว่างได้ไม่ตรงวัตถุประสงค์ flow |
| ประเภทการจ้างงาน, สถานะการจ้างงาน, กลุ่มพนักงาน | C | **ซ้ำซ้อนกันเอง** — 3 ช่องนี้พยายามตอบคำถามคล้ายกัน (พนักงานประเภทไหน สถานะอะไร) แนะนำให้ product ตัดสินใจรวมเป็น 1 concept เดียวก่อนส่งให้ Core ออกแบบ column ไม่ควรขอ Core ทำ 3 field แยกที่ทับซ้อนกัน |
| ประเภทงาน (Full-time/Part-time), รูปแบบการทำงาน (Work Arrangement) | C | มีประโยชน์จริง ไม่ทับซ้อนกับอะไร เก็บไว้ได้ |
| ระดับ (Grade), กลุ่มเงินเดือน (Salary Band), เงินเดือนเริ่มต้น | D | **ข้อมูล compensation** — คนละบริบทกับ "สร้างบัญชีพนักงาน" โดยตรง และปกติมี sensitivity/สิทธิ์การเข้าถึงต่างจาก HR ทั่วไป แนะนำแยกเป็นขั้นตอนถัดไป (เช่น หน้า "กำหนดค่าตอบแทน" ที่จำกัด role) แทนที่จะฝังในฟอร์ม intake ที่ HR ทุกคนกรอกได้ — เป็นประเด็นที่ควรถามทีม security/compliance ก่อน ไม่ใช่ตัดสินใจฝ่ายเดียว |
| ประเภทสัญญาจ้าง (Contract Type) | D | เกี่ยวโยงกับ compensation/legal เช่นกัน พิจารณาย้ายไปกลุ่มเดียวกับข้างบน |
| วันสิ้นสุดทดลองงาน (คาดการณ์), ระยะเวลาทดลองงาน | E → ควรรวมเป็น 1 | ตอนนี้เป็น 2 ช่องแยกอิสระ (free text) ที่ไม่ sync กัน — ควรมีแค่ "ระยะเวลาทดลองงาน" (dropdown) แล้ว **คำนวณวันสิ้นสุดจาก start_date อัตโนมัติ** แทนให้ผู้ใช้กรอกทั้งสองเอง เสี่ยงกรอกไม่ตรงกัน |
| ทีม (Team) | E | free text ไม่มีที่เก็บจริง ซ้ำซ้อนกับ "หน่วยงาน" ที่เป็นของจริงอยู่แล้ว ตัดออกจน Core มี concept ทีมย่อยจริง |
| ผู้บังคับบัญชา (Reporting To), ผู้บังคับบัญชารอง | E → ต้องติดป้ายชัดเจนถ้าจะเก็บต่อ | Core **ไม่มี concept "manager" ในโครงสร้าง Membership เลย** (ยืนยันจาก Core's response doc) ตอนนี้ dropdown ดึงจาก mock data ของ `people/personnel` เท่านั้น — ถ้าจะเก็บต่อ ต้องติดป้าย "ข้อมูลอ้างอิง ยังไม่บันทึกในระบบ" ให้ HR เห็นชัดว่าไม่ใช่ของจริง ไม่ใช่ปล่อยให้ดูเหมือนบันทึกแล้วเงียบๆ (ผู้บังคับบัญชารองมีความจำเป็นต่ำกว่า พิจารณาตัดก่อน) |
| สถานที่ทำงาน (work location) | C | เป็น operational fact จริง (สำนักงานไหน) มีประโยชน์แม้ Core ยังไม่รับ |
| สถานที่ทำงานย่อย / พื้นที่ | E | รายละเอียดลึกเกินความจำเป็นของ intake form ไม่มีระบบจัดการพื้นที่รองรับ ตัดออกก่อน |
| หมายเหตุ (step 2) | C | free-text เสริม เก็บไว้ได้ |

## ข้อเสนอเชิงโครงสร้าง flow

1. ✅ **ทำแล้ว (2026-09-01)** — แก้ bug เลขบัตรประชาชน: เลือกทาง (ก) บังคับจริงในปุ่ม "ถัดไป"
   (`canProceedStep0`) + เพิ่มเครื่องหมาย `*` ให้เห็นชัดในป้ายกำกับ (`requiredMark`)
2. ✅ **ทำแล้ว (2026-09-01)** — วันที่เริ่มงาน (start_date) เป็น required ทั้งใน markup
   (`required`) และ gating logic (`canProceedStep1`) แล้ว — Core ยืนยันด้วยว่า
   `POST /employees` ใหม่จะบังคับ field นี้เช่นกัน
3. **รวม "วันสิ้นสุดทดลองงาน" ให้คำนวณอัตโนมัติจาก start_date + ระยะเวลาทดลองงาน** แทนกรอกแยก 2 ช่อง
   — ยังไม่ทำ (Core ตัดสินใจตัด "ระยะเวลาทดลองงาน" ออกไปเลย เหลือแค่ `probation_end_date` เป็นวันที่จริง
   — รอ endpoint ใหม่ deploy ก่อนจะรื้อ field นี้ในโค้ด เพราะเป็นการเปลี่ยนโครงสร้างข้อมูล ไม่ใช่แค่ UI)
4. ✅ **ทำแล้ว (2026-09-01)** — ยุบ ประเภทการจ้างงาน/สถานะการจ้างงาน/กลุ่มพนักงาน เหลือ dropdown เดียว
   (`EMPLOYMENT_TYPE_OPTIONS`) ตรงกับที่ Core ยืนยันว่าจะรวมเป็น `member_type` เดียว — ยังเป็น UI-only,
   ไม่ได้ส่งเข้า Core เพราะ endpoint ที่รับ `member_type` ยังไม่ deploy
5. **แยกข้อมูล compensation (ระดับ/เงินเดือน/กลุ่มเงินเดือน/ประเภทสัญญาจ้าง) ออกจากฟอร์มนี้** ไปเป็น
   ขั้นตอนหรือหน้าจอที่จำกัดสิทธิ์ผู้เข้าถึงต่างหาก — ประเด็นนี้ควรหารือกับทีม security/compliance
   ก่อนตัดสินใจ ไม่ใช่ผลจากเอกสารนี้ฝ่ายเดียว
6. ✅ **ทำแล้ว (2026-09-01)** — ติดป้าย "ข้อมูลอ้างอิง ยังไม่บันทึกในระบบ" ให้ทุก field ในกลุ่ม E
   (ทีม, ผู้บังคับบัญชา, ผู้บังคับบัญชารอง, สถานที่ทำงานย่อย/พื้นที่) แทนการตัดออก ตาม Product
   decision — เพื่อไม่ให้ HR เข้าใจผิดว่าระบบบันทึกไว้แล้ว โดยไม่ต้องรอผูก Core ก่อน
7. การตัด field กลุ่ม E ออกจาก UI ทั้งหมด — **ระงับไว้ก่อนตามคำสั่ง Product** จนกว่าจะมีเหตุผลใหม่
   หรือมี Core รองรับจริง (รูปภาพพนักงานยังคงปิดใช้งานเหมือนเดิม ไม่ต้องติดป้ายเพิ่มเพราะสื่อความหมาย
   เดียวกันอยู่แล้ว)

## แนวทางดำเนินการ (execution)

ลำดับที่แนะนำ:

1. **Product/Design ตัดสินใจ**: เห็นด้วยกับกลุ่ม A–E ข้างต้นไหม โดยเฉพาะกลุ่ม D (compensation
   แยกสิทธิ์หรือไม่) และ field ไหนในกลุ่ม E ที่จะเก็บต่อแบบติดป้าย vs ตัดออกจริง
   *(เป็นการตัดสินใจเชิง product — วิศวกรไม่ควรเป็นคนตัดสินคนเดียว)*
2. **ส่งกลุ่ม A/B/C ให้ทีม API** ตาม `add-employee-field-requirements.md` — แต่ตอนนี้รู้แล้วว่าอันไหน
   เร่งด่วน (B) อันไหนรอได้ (C) และอันไหนต้องรวม concept ก่อนส่ง (ประเภทการจ้างงาน 3 ช่อง)
3. **Engineering แก้ตาม decision**: bug required, คำนวณวันสิ้นสุดทดลองงานอัตโนมัติ, ตัด/ติดป้าย field
   กลุ่ม E, และย้าย field กลุ่ม D ออกถ้า product ตัดสินใจแยก
4. **อัปเดต `add-employee-field-requirements.md`** ให้ตรงกับ field ที่เหลือจริงหลัง engineering
   แก้ไข — เอกสารนั้นควรสะท้อนสถานะปัจจุบันเสมอ ไม่ใช่ snapshot ของวันที่เขียน

Core ส่ง `docs/api/add-employee-integration-guide.md` กลับมา (ผ่าน artifact ที่ user ส่งให้ดู) —
ยืนยัน endpoint ใหม่ (`POST /tenants/:id/employees`, onboarding checklist GET/PATCH, compensation
PUT) พร้อม field mapping ที่ตรงกับตารางด้านบนแทบทุกจุด **แต่ endpoint เหล่านี้ยังไม่ merge เข้า
branch หลักของ Core และยังไม่ deploy** — เช็คกับ user แล้วว่ายังไม่ยืนยันสถานะ deploy จึงทำเฉพาะงาน
ที่ไม่ต้องพึ่ง endpoint ใหม่ (§9 ข้อ 1, 2, 4 บางส่วน) ในรอบนี้:

| งานจาก Core's §9 "งานฝั่ง Frontend" | สถานะ |
|---|---|
| 1. แก้ bug เลขบัตรประชาชน | ✅ ทำแล้ว |
| 2. วันที่เริ่มงานเป็น required | ✅ ทำแล้ว |
| 3. สถานที่ทำงาน → query จาก `locations` จริง | ⏸ ยังไม่ทำ — ไม่มีรายละเอียด endpoint `GET locations` ในเอกสาร และ endpoint ใหม่ยังไม่ deploy |
| 4. ตัด/ติดป้าย field กลุ่ม E ที่เหลือ | ✅ ทำไปแล้วตั้งแต่รอบก่อนหน้า (ตรงกับที่ Core ยืนยันสำหรับผู้บังคับบัญชา) — ข้อเสนอใหม่ของ Core สำหรับ "ทีม" (ทำเป็น child department) ยังเป็นแค่ข้อเสนอ ไม่ใช่ decision (§7 เองก็บอกว่า "ต้องตัดสินใจร่วมกันก่อน") จึงยังไม่รื้อ |
| 5. รวม 3 ช่องเหลือ `member_type` เดียว | ✅ ทำแล้ว (UI-only — ยังไม่ส่งค่าเข้า Core) |

**ยังไม่ได้ทำ (รอ deploy ก่อน)**: เปลี่ยนไปเรียก `POST /employees` จริงแทน `POST /members`, ส่ง field
ใหม่ทั้งหมด (`national_id`, `date_of_birth`, `gender`, `member_type`, `default_location_id` ฯลฯ)
เข้า Core, ต่อ onboarding checklist endpoint แทนการ fabricate ฝั่ง client, ต่อ compensation
endpoint. เมื่อ Core ยืนยันว่า deploy แล้ว ค่อยกลับมาทำส่วนนี้ต่อ.
