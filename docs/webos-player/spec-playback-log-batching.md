# Playback log: ส่งเป็นชุดพร้อมรอบ poll

**ถึง:** ทีม Player · **จาก:** ทีม Core · **วันที่:** 2026-11-12
**API ที่เกี่ยว:** `POST /api/core/v1/media/player/playback` (ไม่มีการเปลี่ยนแปลงฝั่ง Core)

## สรุป

ตอนนี้ Player ส่ง playback log **ทุกครั้งที่คลิปเล่นจบ** สัญญาเดิมออกแบบให้ **เก็บไว้ในเครื่องแล้วส่งเป็นชุดทีเดียวตอน poll** ขอให้ปรับตามสเปกด้านล่าง

```
ตอนนี้                                   ที่ต้องการ
คลิปจบ ─► POST (1 รายการ)                คลิปจบ ─► เขียนลง queue บน disk
คลิปจบ ─► POST (1 รายการ)                คลิปจบ ─► เขียนลง queue บน disk
คลิปจบ ─► POST (1 รายการ)                ...
...                                      ถึงรอบ poll ─► POST (ทุกรายการใน queue, ≤500)
≈ 6 ครั้ง/นาที (คลิป 11 วิ)                1 ครั้ง/นาที
```

## หลักฐาน (prod, 5–12 พ.ย. 2026, 20 จอ)

| ตัวชี้วัด | ค่า |
|---|---|
| request playback ทั้งหมด | 367K (52% ของ request ที่เข้า Core) |
| heartbeat / jobs (ปกติ ~1 ครั้ง/นาที) | 151K / 149K |
| รายการเฉลี่ยต่อ request | 1.23 |
| request ที่มีแค่ 1 รายการ | 85% |
| จอที่ส่งถี่ที่สุด (คลิปเฉลี่ย 11 วิ) | 14,944 ครั้ง/วัน ≈ 10 ครั้ง/นาที |

ผลที่คาดไว้: playback เหลือไม่เกิน 1,440 ครั้ง/วัน/จอ และ request รวมของ Core ลดลงราว 40–50%

## สเปก

### 1. เก็บรายการ
- พอคลิปเล่นจบ (`played` / `failed` / `interrupted`) ให้เขียนรายการลง **queue ที่อยู่บน disk** (ไม่ใช่ memory) เพื่อไม่ให้หายตอนไฟดับ
- เก็บ `played_at` เป็น ISO-8601 string ที่มี offset (เช่น `2026-11-12T14:03:21.000+07:00`) ตั้งแต่ตอนเขียน และ**ห้ามสร้างค่าใหม่ตอน retry** เพราะ Core ใช้ `(device, asset, played_at, zone)` เป็นตัวกันข้อมูลซ้ำ
- field อื่นเหมือนเดิมทุกอย่าง

### 2. จังหวะส่ง
- ส่งตอนถึงรอบ poll (ตาม `next_poll_after_seconds` จาก `/media/player/jobs`) **หรือ** ทันทีที่ queue มีครบ 500 รายการ
- แต่ละ request ส่งได้ไม่เกิน **500 รายการ** เรียงจากเก่าสุด
- ถ้า queue มีมากกว่า 500 (เช่นเพิ่งกลับมาออนไลน์) ให้ส่ง **ทีละ chunk** รอให้ chunk ก่อนหน้าได้ผลก่อนแล้วค่อยส่งตัวถัดไป อย่ายิงพร้อมกันทั้งหมด

### 3. จัดการผลตอบกลับ

| ผลตอบกลับ | ความหมาย | ต้องทำอะไร |
|---|---|---|
| **2xx** | บันทึกแล้ว (`logged + duplicates` = จำนวนที่ส่ง) | ลบรายการที่ส่งไปออกจาก queue |
| **5xx**, timeout, network error | ปัญหาชั่วคราว | เก็บไว้ แล้ว retry แบบ backoff (ไม่นานเกินรอบ poll) |
| **400** หรือ **404** | มีรายการในชุดนี้ที่ผิด (Core ปฏิเสธ**ทั้งชุด**) | แบ่ง chunk ครึ่งหนึ่งแล้วส่งใหม่ทีละครึ่ง ทำซ้ำจนเหลือรายการเดียว รายการที่ส่งเดี่ยวแล้วยังได้ 400/404 ให้**ทิ้ง** และจด log ในเครื่องพร้อมข้อความ error |
| **401** | token ไม่ถูกต้องหรือถูก revoke | หยุดส่ง แต่เก็บ queue ไว้ |

> ⚠️ ข้อ 400/404 สำคัญที่สุด ถ้าทำแค่ "ลบเมื่อได้ 2xx" แล้วมีรายการผิดหนึ่งรายการค้างอยู่ใน queue ชุดนั้นจะถูก reject ทุกรอบ และ log ทั้งหมดของจอนั้นจะค้างไปตลอด

```
ส่ง chunk ─┬─ 2xx ──────────► ลบออกจาก queue
           ├─ 5xx/timeout ──► เก็บไว้ ลองใหม่รอบหน้า
           ├─ 401 ──────────► หยุดส่ง เก็บ queue ไว้
           └─ 400/404 ──► chunk มีมากกว่า 1 รายการ? ─ ใช่ ─► แบ่งครึ่ง ส่งใหม่ทีละครึ่ง
                                                  └ ไม่ ─► ทิ้งรายการนี้ + จด log ในเครื่อง
```

### 4. ขนาด queue
- จำกัดไว้ที่ **10,000 รายการ หรือ 7 วัน** ถ้าเกินให้ทิ้งรายการเก่าสุดก่อน

## สิ่งที่ไม่เปลี่ยน
- URL, request body, response และ auth (`Authorization: Bearer <device token>`) เหมือนเดิมทุกอย่าง
- heartbeat และ jobs poll ยังทำงานเหมือนเดิม **อย่า**รวม playback log เข้าไปใน heartbeat เพราะ heartbeat ถูกออกแบบให้ไม่ fail เพื่อไม่ให้จอที่ยังทำงานถูกมองว่า offline
- log ที่มาช้า (แม้หลายชั่วโมง) Core ยังรับได้ และจะแสดงตาม `played_at` ที่ถูกต้อง

## วิธีเช็คว่าทำถูก
1. เปิดจอทิ้งไว้ 10 นาที → ฝั่ง Core ควรเห็น playback request ประมาณ 10 ครั้ง (ไม่ใช่ 50+ ครั้ง)
2. ถอดสายเน็ต 30 นาทีแล้วเสียบกลับ → log ที่ค้างอยู่ทยอยเข้ามาเป็น chunk และใน Playback Proof เห็นเวลาเล่นตรงกับช่วงที่ offline
3. ทดลองใส่รายการผิดหนึ่งรายการ (เช่น `media_asset_id` ที่ไม่มีอยู่จริง) ลงใน queue → รายการนั้นถูกทิ้ง ส่วนรายการอื่นในชุดเดียวกันยังเข้ามาครบ
