# account-security

`/account-security` — new 2026-09-16, part of the shell redesign alongside `profile`. Reached from `UserMenu`'s "บัญชีและความปลอดภัย" item and from the dedicated settings sidebar (`Sidebar.tsx`'s `SettingsSidebar`, shown on `/profile` and `/account-security`).

> **Almost entirely inert by necessity, not by choice.** Checked directly against `thunder_core_API` (`develop` branch) — grepped every route under `api/core/v1/*` on 2026-09-16: password change, MFA, device/session management, login-activity, and a phone field have **zero backing anywhere** — no Core route, no DB table. Core's own internal dashboard does these by calling Supabase Auth's client SDK directly (`supabase.auth.updateUser`/`mfa.*`), a pattern this app doesn't have (no Supabase client set up, and this app's session is Core's own bearer cookie, not a Supabase SSR session). Every section below is built to match the mockup's visual language (colors/icons/card layout — Figma node 341:3520) but the *values* stay honest placeholders — no fabricated device list, no fake "MFA enabled"/security-checklist green checks, no invented phone number. Same trap Core's *own* internal "Security & Privacy" dashboard fell into with a hardcoded "128 active sessions" (found during research — a cautionary example, not something to copy).

- `components/AccountSecurityPage.tsx`:
  - Profile-summary card — real (reuses `profile`'s own `getMyProfile`/`CoreMe`, same person, no point duplicating the fetch). Email row has a real "ใช้งานอยู่" badge (true by definition — it's the address the current session is authenticated with, not a verification claim). Username row has a real, working copy-to-clipboard button (only rendered when `global_user_code` is set). Phone row is an honest "ยังไม่มีข้อมูลในระบบ" — no phone field exists on `/me`.
  - Password card — real "-" last-updated (no data source; strength is unknowable to the frontend in principle, since it never sees the plaintext), opens `ChangePasswordModal`.
  - MFA card, security-status card, login-activity card — inert, explicit notes, styled to match the mockup's card layout.
  - "อุปกรณ์ที่เข้าสู่ระบบ" (connected devices) — **added back 2026-09-16** (an earlier pass had deliberately left it out); the mockup shown this round included it, so it's now present as an honest empty state ("ยังไม่สามารถตรวจสอบอุปกรณ์ที่เข้าสู่ระบบบัญชีนี้ได้ในขณะนี้") rather than a fabricated device list.
  - "ความปลอดภัยเพิ่มเติม" links — inert list items (chevron row style matching the mockup), each `title="ยังไม่พร้อมใช้งาน"`.
- `components/ChangePasswordModal.tsx` — the 6-step mockup's flow, but only steps 1-3 (form with real-time strength checklist → validating) are real; step 3 always resolves to an honest "ฟีเจอร์นี้ยังไม่เปิดใช้งานในตอนนี้" state instead of a fabricated success screen. See the component's own header comment for exactly what's missing (a Supabase client + session-token bridging) before this could work for real.
