# account-security

`/account-security` — new 2026-09-16, part of the shell redesign alongside `profile`. Reached only from `UserMenu`'s "บัญชีและความปลอดภัย" item, not the sidebar.

> **Almost entirely inert by necessity, not by choice.** Checked directly against `thunder_core_API` (routes and DB migrations both): password change, MFA, device/session management, and login-activity logs have **zero backing anywhere** — no Core route, no DB table. Core's own internal dashboard does these by calling Supabase Auth's client SDK directly (`supabase.auth.updateUser`/`mfa.*`), a pattern this app doesn't have (no Supabase client set up, and this app's session is Core's own bearer cookie, not a Supabase SSR session). Every section below is built to match the mockup visually but stays honestly inert — no fabricated device list, no fake "MFA enabled"/security-checklist green checks, matching the same trap Core's *own* internal "Security & Privacy" dashboard fell into with a hardcoded "128 active sessions" (found during research — a cautionary example, not something to copy).

- `components/AccountSecurityPage.tsx` — profile-summary card (real, reuses `profile`'s own `getMyProfile`/`CoreMe` — same person, no point duplicating the fetch), password card (real "-" last-updated, opens `ChangePasswordModal`), MFA card (inert, explicit note), security-status/login-activity/additional-security cards (all inert/empty, explicit notes). **The mockup's "อุปกรณ์ที่เข้าสู่ระบบ" (connected devices) section was deliberately left out** — the source mockup itself marked it for removal.
- `components/ChangePasswordModal.tsx` — the 6-step mockup's flow, but only steps 1-3 (form with real-time strength checklist → validating) are real; step 3 always resolves to an honest "ฟีเจอร์นี้ยังไม่เปิดใช้งานในตอนนี้" state instead of a fabricated success screen. See the component's own header comment for exactly what's missing (a Supabase client + session-token bridging) before this could work for real.
