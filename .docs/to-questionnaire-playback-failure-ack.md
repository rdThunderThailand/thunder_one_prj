# แยก Playback Failure ออกจาก Delivery Failure — แบบสอบถามสำหรับทีม Player/Device

**วัตถุประสงค์:** ฟีเจอร์ delivery-progress ของ publication (ClickUp ticket 86d3xxr09) ควรบอกได้ว่าจอ
พังตรงไหน — ไฟล์ไม่ถึงเครื่อง หรือถึงเครื่องแล้วแต่เปิดไม่ติด ตอนนี้เราแยกสองอย่างนี้ไม่ได้เลย
อยากให้ทีม player ช่วยตอบว่า protocol ปัจจุบันส่งข้อมูลพอแยกได้ไหม และถ้าไม่พอ ต้องทำอะไรเพิ่ม

**จาก:** ทีม Thunder One frontend/platform — **ถึง:** ทีม Player/Device — **คำตอบจะถูกใช้ที่ไหน:**
ใช้ตัดสินใจว่าจะ scope งานแก้ protocol ในไตรมาสนี้ไหม หรือบันทึกไว้เป็นข้อจำกัดแล้วพักไว้ก่อน
คำตอบอาจถูกนำไปเขียนต่อใน ADR และ ticket ตามมา

## บริบท

เพิ่งปล่อยหน้าจอ delivery-progress ที่โชว์ 3 stage ต่อจอ: media ready → delivered to device →
playback confirmed ตอนนี้ device ack สถานะกลับมาผ่าน `POST /player/jobs/{target_id}/ack`
(หลังบ้านคือ `media_job_ack`) ส่งค่าใดค่าหนึ่งใน `downloading`, `delivered`, `playing`, `failed`
พร้อม error message เป็น free text (optional) และ `media_asset_id` สำหรับ per-file ack (optional)
เราเก็บแค่สถานะล่าสุดที่ส่งมา — ไม่มีประวัติว่า target ผ่านอะไรมาก่อนจะถึงสถานะนั้น

**ปัญหา:** `failed` เป็น bucket เดียว ถ้า device ส่ง `status: "failed"` มา เราแยกไม่ออกว่าเกิดจาก
ไฟล์ยังโหลด/apply ไม่เสร็จ หรือโหลดเสร็จแล้วแต่เปิดเล่นไม่ได้ (codec ไม่รองรับ, ไฟล์เสีย, decoder
crash ฯลฯ) ticket ของเรามี AC สองข้อที่ขอให้แยกสองอย่างนี้ตรงๆ — AC ของ playback confirmation
บอกว่า device ที่ "ดาวน์โหลดสำเร็จแต่เปิดสื่อไม่ได้ ต้องแสดง Playback Failed" (แยกจาก error ตอน
delivery) และ AC ของ error handling ก็ขอให้ทุก error ระบุว่าเกิดใน state ไหน ตอนนี้เราทำตาม AC
สองข้อนี้ตรงๆ ไม่ได้ — โค้ดฝั่ง frontend มี workaround ที่เขียน comment กำกับไว้ชัดเจนว่าจับทุก
`failed` ว่าเป็น "delivery failure" เสมอ เพราะเป็นสิ่งเดียวที่เรายืนยันได้จริง ทั้งที่บางเคสอาจ
เป็น playback failure จริงๆ ก็ได้

## วิธีตอบ

ไม่มี deadline ตายตัว — คำตอบนี้เอาไปใช้วางแผนงานรอบถัดไป ไม่ได้บล็อกงานตอนนี้ ถ้าไม่แน่ใจข้อไหน
ให้บอกตรงๆ ว่า "ไม่แน่ใจ" ดีกว่าข้ามไป เดาเวลาที่ใช้ตอบ: 15-20 นาทีถ้าคุ้นโค้ด player อยู่แล้ว
นานกว่านั้นถ้าต้องไปเช็คกับคนที่ดูแล player app/firmware โดยตรง

## Protocol ปัจจุบันและความสามารถของ player

### ตอนนี้ player รู้ภายในตัวเองไหมว่า failure เกิดตอน download/apply หรือตอน playback?

_ทำไมถึงถาม: ถ้า player รู้อยู่แล้วภายในแต่แค่ไม่ได้ส่งกลับมา นี่คือการแก้ protocol แบบเล็ก
แต่ถ้า player แยกไม่ออกจริงๆ ตั้งแต่ต้น นี่คืองานใหญ่กว่านั้นที่ต้องแก้ในตัว player เอง_

>

### failure mode จริงๆ ที่เกิดขึ้นตอน device มีไฟล์แล้วแต่เปิดเล่นไม่ได้ มีอะไรบ้าง?

ตัวอย่างที่เราเดาไว้: codec ไม่รองรับ, ไฟล์เสียแต่ผ่าน checksum มาได้, decoder crash,
storage/memory ไม่พอตอนจะเล่น, file reference หมดอายุหรือผิดรูปแบบ — ช่วยแก้/เพิ่มลิสต์นี้ตามที่
เจอจริงในหน้างานด้วย

>

### ตอนนี้ playback failure เคยถูกรายงานกลับมาทางช่องทางอื่นบ้างไหม (log, crash report, heartbeat, อะไรก็ได้) แม้จะไม่ผ่าน `media_job_ack`?

_ทำไมถึงถาม: ถ้าข้อมูลนี้มีอยู่แล้วที่อื่น (เช่น device log ที่ดึงได้) เราอาจไม่ต้องแก้ protocol
เลยก็ได้_

>

## ข้อเสนอแก้ protocol

### ถ้าจะให้ ack ส่งค่าที่แยก "โหลดมาแล้วแต่เปิดเล่นไม่ได้" ออกมาต่างหาก — เช่น status ใหม่ `playback_failed` หรือ field แยกต่างหากจาก `status`/`error` — ทีม player โอเคไหม?

_ทำไมถึงถาม: อยากให้ตรงกับวิธีที่ทีม player คิดเรื่อง state machine ของตัวเองอยู่แล้ว มากกว่าจะ
ยัดรูปแบบที่ไม่เข้ากับของเดิม_

>

### ถ้าทำ ต้องรอ firmware/app update ถึงจะใช้ได้ หรือ device ที่ deploy อยู่แล้วส่งค่านี้ได้เลยทันทีที่ backend รองรับ?

_ทำไมถึงถาม: จะได้รู้ว่านี่คือ "แก้ backend + รอ player release รอบหน้า" หรือ "แก้ backend + รอ
ทั้ง fleet update" ซึ่งกำหนดว่า operator จะเห็นความแตกต่างนี้เร็วแค่ไหน_

>

### มีเหตุผลที่ไม่ควรแยกแบบนี้ไหม — เช่น player ไม่รู้จริงๆ ว่าตอนพังอยู่ stage ไหน ค่าที่ส่งมาจะกลายเป็นแค่การเดา?

_ทำไมถึงถาม: เราไม่อยากได้ field ที่ดูแม่นยำแต่จริงๆ player แค่เดา — แบบนั้นแย่กว่าการบอกตรงๆ ว่า
"ไม่รู้" แบบที่เป็นอยู่ตอนนี้_

>
