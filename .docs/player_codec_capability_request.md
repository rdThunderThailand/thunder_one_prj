# ขอข้อมูล codec ที่จอรองรับ — เพื่อกำหนดเป้าหมายของ transcoding pipeline

**สำหรับ:** ทีมที่ทำ firmware ของจอ (player)
**จาก:** ทีม Thunder backend/frontend
**เอกสารคู่กัน:** `player_contract_timeline.md` (สัญญาของ endpoint poll) — ไม่ต้องอ่านก่อนก็ได้ เอกสารนี้อ่านจบได้ด้วยตัวเอง
**วันที่:** 2026-08-14
**สถานะ:** ⛔ **บล็อกงานฝั่งเราอยู่** — เราเริ่มเขียน pipeline ไม่ได้จนกว่าจะได้คำตอบ

---

## สรุปสั้น (อ่าน 30 วินาที)

ตอนนี้ระบบรับอัปโหลดได้แค่ `.mp4` ถ้า user มีไฟล์ `.mov` จากมือถือ ต้องไปแปลงเองก่อน ซึ่งไม่โอเค

เรากำลังจะทำระบบที่ **รับไฟล์วิดีโออะไรก็ได้ แล้วแปลงเป็น mp4 ให้อัตโนมัติ** ก่อนส่งเข้าคิวของจอ

**ปัญหาคือเราไม่รู้ว่าจะแปลงไปเป็นอะไร** — ถ้าเราตั้งเป้าสูงเกินไป จอจะเล่นไม่ออกหรือกระตุก ถ้าตั้งต่ำเกินไป ภาพจะแตกโดยไม่จำเป็น

**เราต้องการ 6 ค่าจากคุณ** (รายละเอียดในหัวข้อถัดไป):

| # | ต้องการรู้ | ถ้าไม่รู้จะเกิดอะไร |
|---|---|---|
| 1 | H.264 profile/level สูงสุดที่ decode ได้ | ไฟล์เล่นไม่ออก หรือกระตุกบนจอ |
| 2 | ความละเอียดสูงสุด | เสีย bandwidth + storage ฟรีๆ หรือภาพแตก |
| 3 | fps สูงสุด | วิดีโอ 60fps กระตุก |
| 4 | รองรับ HEVC (H.265) มั้ย | ถ้ารองรับ เราประหยัดขนาดไฟล์ได้ ~40% |
| 5 | จอเล่นเสียงมั้ย | ถ้าไม่เล่น เราตัด audio ทิ้งได้เลย ไฟล์เล็กลงอีก |
| 6 | เล่นไฟล์ `.mov` ได้มั้ย | **ข้อนี้อาจลบงานทั้งก้อนของเราทิ้งได้** — ดูคำอธิบายใน Q6 |

**ตอบกลับได้ 3 ทาง เลือกทางไหนก็ได้** — ทางที่ 3 (ทดสอบจริง) เชื่อถือได้ที่สุด และเราแนะนำให้ทำถ้ามีเวลา

## ทำไมถึงถาม (บริบทที่จำเป็น)

ทุกวันนี้ flow เป็นแบบนี้:

```
user เลือกไฟล์ → อัปขึ้น storage ตรงๆ → จอ poll → จอโหลดไฟล์นั้นไปเล่น
```

**ไม่มีขั้นตอนไหนแตะไฟล์เลย** สิ่งที่ user อัปคือสิ่งที่จอได้เป๊ะๆ เราจึงต้องบังคับให้ user อัปแต่ `.mp4` เพราะเราไม่กล้าเดาว่าอย่างอื่นจอจะเล่นออกมั้ย

ของใหม่จะเป็น:

```
user เลือกไฟล์อะไรก็ได้ → อัปขึ้น storage → [ ระบบแปลงเป็น mp4 ตามสเปกของจอ ] → จอ poll → จอโหลดไปเล่น
```

ขั้นที่อยู่ในวงเล็บคือสิ่งที่เรากำลังจะสร้าง และ **"สเปกของจอ" คือสิ่งที่เราไม่มี**

หมายเหตุที่คุณอาจสนใจ: จอ**จะไม่เห็นไฟล์ระหว่างที่กำลังแปลง** — asset จะอยู่สถานะ `processing` จนแปลงเสร็จ พอเสร็จแล้ว `storage_key` กับ `checksum` จะเป็นของไฟล์ใหม่เลย **คุณไม่ต้องแก้ firmware เพื่อรองรับเรื่องนี้** ไม่มีเคสที่จอโหลดไฟล์ไปแล้วไฟล์เปลี่ยนใต้เท้า

## 5 คำถาม

### Q1 — H.264 profile และ level สูงสุดที่ decode ได้

H.264 มี profile หลายระดับ (`Baseline` < `Main` < `High`) และ level หลายระดับ (`3.0`, `4.0`, `4.2`, ...) ชิป decode ของแต่ละรุ่นรองรับไม่เท่ากัน

- ถ้าจอรองรับแค่ `Baseline` แล้วเราส่ง `High` ไป → **เล่นไม่ออกเลย หรือภาพเพี้ยน**
- ถ้าจอรองรับ `High` แต่เราส่ง `Baseline` → เล่นได้ แต่ไฟล์ใหญ่กว่าที่ควรประมาณ 10–20% ที่คุณภาพเท่ากัน

**ต้องการ:** profile สูงสุด + level สูงสุด เช่น `High@4.0`

### Q2 — ความละเอียดสูงสุด

ถ้าจอเป็น 1080p แต่ user อัปไฟล์ 4K มา เราควรย่อเหลือ 1080p ก่อนส่ง — จอจะได้ไม่ต้องเปลือง CPU ย่อเอง และประหยัด bandwidth ตอนโหลด

**ต้องการ:** ความละเอียดจริงของหน้าจอ (เช่น `1920x1080`) และความละเอียดสูงสุดที่ decoder รับได้ ถ้าไม่เท่ากัน

> ถ้ามีจอหลายรุ่นในระบบที่ spec ไม่เท่ากัน **บอกมาทุกรุ่น** เราจะตั้งเป้าที่รุ่นต่ำสุด (หรือคุยกันเรื่องทำหลาย version)

### Q3 — fps สูงสุด

มือถือสมัยใหม่อัด 60fps เป็นเรื่องปกติ ถ้า decoder ของจอไหวแค่ 30fps เราต้องลดให้ก่อน ไม่งั้นภาพจะกระตุก

**ต้องการ:** fps สูงสุดที่เล่นได้ลื่นที่ 1080p

### Q4 — รองรับ HEVC (H.265) มั้ย

HEVC ให้คุณภาพเท่า H.264 ที่ขนาดไฟล์เล็กกว่าประมาณ 40% — ถ้าจอรองรับ เราจะประหยัดทั้ง storage และเวลาโหลดของจอมาก

แต่ HEVC decode หนักกว่า และชิปรุ่นเก่าหลายตัวไม่รองรับ **ถ้าไม่แน่ใจ ตอบว่าไม่รองรับ** เราจะใช้ H.264 ซึ่งปลอดภัยกว่า

**ต้องการ:** รองรับ / ไม่รองรับ / ไม่แน่ใจ

### Q5 — จอเล่นเสียงมั้ย

ป้ายโฆษณาส่วนมากปิดเสียง ถ้าจอไม่มีลำโพงหรือไม่เคยเปิดเสียงเลย เราจะ**ตัด audio track ทิ้งตอนแปลง** ไฟล์เล็กลงอีกโดยไม่เสียอะไร

**ต้องการ:** เล่นเสียง / ไม่เล่นเสียง · ถ้าเล่น รองรับ codec อะไร (ปกติคือ AAC)

### Q6 — เล่นไฟล์ `.mov` ได้มั้ย (ถ้าข้างในเป็น H.264) ← ข้อนี้อาจทำให้เราไม่ต้องทำอะไรเลย

ขออธิบายก่อนเพราะข้อนี้ฟังดูเป็นรายละเอียดเล็กๆ แต่จริงๆ แล้วสำคัญที่สุดข้อหนึ่ง

`.mov` (QuickTime) กับ `.mp4` เป็น**รูปแบบไฟล์ตระกูลเดียวกัน** (ISOBMFF) ต่างกันแค่ "กล่อง" ข้างนอก วิดีโอที่อยู่ข้างในเป็นข้อมูลชุดเดียวกันเป๊ะ — ไฟล์ `.mov` จากมือถือส่วนใหญ่ข้างในคือ H.264 ตัวเดียวกับที่อยู่ใน `.mp4`

- **ถ้าจอเล่น `.mov` ที่ข้างในเป็น H.264 ได้** → เราแค่อนุญาตให้อัป `.mov` ได้เลย **ไม่ต้องแปลงอะไรทั้งนั้น** งานฝั่งเราหายไปเกือบทั้งหมด
- **ถ้าเล่นไม่ได้** → เราต้องเขียนระบบแปลงกล่อง `.mov` → `.mp4` ซึ่งเป็นงานหลายสัปดาห์

ถ้าตอบข้อนี้ได้ข้อเดียวก็คุ้มค่าที่เราเขียนเอกสารนี้แล้ว

**ต้องการ:** เล่น `.mov` ได้ / ไม่ได้ / ไม่แน่ใจ — และถ้าพอทดสอบได้ ขอผลจากการลองเล่นจริง (ไฟล์ `t_h264_in_mov.mov` ในชุดทดสอบข้างล่าง) มากกว่าคำตอบจาก spec

> คำใบ้: ถ้า firmware ใช้ ExoPlayer / libVLC / ffmpeg อยู่ข้างใน คำตอบมักจะเป็น "ได้" · ถ้าเรียก decoder ของ SoC ตรงๆ โดยดูจากนามสกุลไฟล์ มักจะเป็น "ไม่ได้"

## วิธีหาคำตอบ — เลือกทางไหนก็ได้

### ทาง 1 — ดูจาก spec sheet ของชิป (เร็วที่สุด)

ถ้ารู้ว่าจอใช้ SoC รุ่นอะไร (เช่น Amlogic S905X4, Rockchip RK3568, RPi 4) ค้น spec sheet แล้วดูหัวข้อ "Video Decoder" จะมีบอกครบทั้ง profile, ความละเอียด, fps, HEVC

**บอกชื่อรุ่น SoC มาก็พอ** ถ้าไม่อยากค้นเอง เราค้นให้ได้

### ทาง 2 — ถาม Android โดยตรง (ถ้าจอเป็น Android)

ถ้า firmware รันบน Android ระบบตอบเองได้เลย ไม่ต้องเดา:

```bash
adb shell dumpsys media.player | grep -i -A5 "avc\|hevc"
```

หรือใน code:

```kotlin
val codecs = MediaCodecList(MediaCodecList.REGULAR_CODECS)
for (info in codecs.codecInfos) {
    if (info.isEncoder) continue
    for (type in info.supportedTypes) {
        if (type != "video/avc" && type != "video/hevc") continue
        val caps = info.getCapabilitiesForType(type)
        println("=== ${info.name} / $type ===")
        for (p in caps.profileLevels) {
            println("  profile=${p.profile} level=${p.level}")
        }
        val v = caps.videoCapabilities
        println("  width=${v.supportedWidths}  height=${v.supportedHeights}")
        println("  fps@1080p=${v.getSupportedFrameRatesFor(1920, 1080)}")
    }
}
```

**ส่ง output ดิบมาได้เลย ไม่ต้องแปล** เราอ่านเองได้

### ทาง 3 — ทดสอบจริงด้วยไฟล์ทดสอบ (เชื่อถือได้ที่สุด — แนะนำ)

spec sheet โกหกได้ ของจริงไม่โกหก ถ้ามีเวลา 20 นาที ทางนี้ให้คำตอบที่เราเชื่อได้ 100%

**สร้างไฟล์ทดสอบ** (รันบนเครื่องไหนก็ได้ที่มี `ffmpeg`) — หรือ**บอกเรา เราสร้างส่งให้ได้**:

```bash
# ไฟล์ต้นทางสำหรับทดสอบ: สี่เหลี่ยมเคลื่อนที่ 10 วินาที มีตัวเลขนับเฟรม
ffmpeg -f lavfi -i testsrc=size=1920x1080:rate=60:duration=10 \
       -f lavfi -i sine=frequency=440:duration=10 \
       -c:v libx264 -profile:v high -level 4.2 -pix_fmt yuv420p \
       -c:a aac -movflags +faststart t_high42_1080p60.mp4

ffmpeg -f lavfi -i testsrc=size=1920x1080:rate=30:duration=10 \
       -c:v libx264 -profile:v high -level 4.0 -pix_fmt yuv420p \
       -an -movflags +faststart t_high40_1080p30.mp4

ffmpeg -f lavfi -i testsrc=size=1920x1080:rate=30:duration=10 \
       -c:v libx264 -profile:v main -level 4.0 -pix_fmt yuv420p \
       -an -movflags +faststart t_main40_1080p30.mp4

ffmpeg -f lavfi -i testsrc=size=1920x1080:rate=30:duration=10 \
       -c:v libx264 -profile:v baseline -level 3.1 -pix_fmt yuv420p \
       -an -movflags +faststart t_base31_1080p30.mp4

ffmpeg -f lavfi -i testsrc=size=3840x2160:rate=30:duration=10 \
       -c:v libx264 -profile:v high -level 5.1 -pix_fmt yuv420p \
       -an -movflags +faststart t_high51_4k30.mp4

ffmpeg -f lavfi -i testsrc=size=1920x1080:rate=30:duration=10 \
       -c:v libx265 -pix_fmt yuv420p -tag:v hvc1 \
       -an -movflags +faststart t_hevc_1080p30.mp4

# สำหรับ Q6: ข้างในเหมือน t_high40_1080p30.mp4 ทุกอย่าง ต่างแค่กล่องเป็น .mov
ffmpeg -f lavfi -i testsrc=size=1920x1080:rate=30:duration=10 \
       -c:v libx264 -profile:v high -level 4.0 -pix_fmt yuv420p \
       -an -f mov t_h264_in_mov.mov
```

**เอาไปเล่นบนจอจริง แล้วกาตาราง:**

| ไฟล์ | เล่นออกมั้ย | ลื่นมั้ย | หมายเหตุ |
|---|---|---|---|
| `t_base31_1080p30.mp4` | ☐ ได้ ☐ ไม่ได้ | ☐ ลื่น ☐ กระตุก | |
| `t_main40_1080p30.mp4` | ☐ ได้ ☐ ไม่ได้ | ☐ ลื่น ☐ กระตุก | |
| `t_high40_1080p30.mp4` | ☐ ได้ ☐ ไม่ได้ | ☐ ลื่น ☐ กระตุก | |
| `t_high42_1080p60.mp4` | ☐ ได้ ☐ ไม่ได้ | ☐ ลื่น ☐ กระตุก | มีเสียงมั้ย: ☐ มี ☐ ไม่มี |
| `t_high51_4k30.mp4` | ☐ ได้ ☐ ไม่ได้ | ☐ ลื่น ☐ กระตุก | |
| `t_hevc_1080p30.mp4` | ☐ ได้ ☐ ไม่ได้ | ☐ ลื่น ☐ กระตุก | |
| `t_h264_in_mov.mov` | ☐ ได้ ☐ ไม่ได้ | ☐ ลื่น ☐ กระตุก | **ข้อสำคัญ (Q6)** — ข้างในเหมือน `t_high40_1080p30.mp4` เป๊ะ ต่างแค่นามสกุล |

> **"กระตุก" นับว่าไม่ผ่าน** — decoder ที่ตกเฟรมคือ decoder ที่ทำไม่ไหว ไม่ใช่ decoder ที่รองรับ
> ทดสอบด้วยไฟล์ที่โหลดลงเครื่องแล้ว (ไม่ใช่ stream) เพื่อไม่ให้ปนกับปัญหาเน็ต

## แบบฟอร์มตอบกลับ

ก๊อปบล็อกนี้ไปเติมแล้วส่งกลับมาได้เลย — ไม่ต้องเขียนอธิบาย เติมค่าอย่างเดียวพอ
ช่องไหนไม่รู้ให้ใส่ `unknown` **อย่าเดา** เราจะใช้ค่า conservative แทนให้เอง

```yaml
# ตอบโดย: <ชื่อ/ทีม>
# วันที่: <YYYY-MM-DD>
# ตอบจาก: spec_sheet | android_query | tested_on_device   ← ระบุด้วยว่าได้มาจากทางไหน

screen_model: "<รุ่นจอ หรือ 'มีหลายรุ่น' แล้วแยกตอบข้างล่าง>"

  mov_supported: "<yes | no | unknown>"
  mov_tested_on_device: "<yes | no>"

```

**ส่งกลับยังไงก็ได้ที่สะดวก** — ก๊อป YAML วางในแชท, แนบไฟล์, หรือตอบเป็นข้อความธรรมดาก็ได้ ขอแค่ค่าครบ ไม่ต้องจัดรูปแบบให้สวย

**ตอบเป็นงวดได้** ไม่ต้องรอให้ครบทุกข้อ — ถ้าตอบ Q1 กับ Q6 ได้ก่อน ส่งมาก่อนเลย สองข้อนั้นปลดล็อกงานฝั่งเราได้มากที่สุด ที่เหลือตามมาทีหลังได้

**ถ้าตอบไม่ได้เลยภายในกำหนด บอกมาสั้นๆ ก็พอ** เราจะเดินงานต่อด้วยค่า conservative แล้วมาปรับทีหลัง — เราไม่อยากให้เอกสารนี้ไปค้างเป็นงานที่บล็อกฝั่งคุณ

## เราจะทำอะไรกับคำตอบ

เพื่อให้เห็นภาพว่าคำตอบแต่ละแบบเปลี่ยนอะไร:

| คำตอบที่ได้ | เราจะตั้ง encode target เป็น |
|---|---|
| `high` / `4.0` / `1080p` / `30` / HEVC ไม่รองรับ / ไม่มีเสียง | `libx264 -profile:v high -level 4.0`, ย่อลง 1080p, cap 30fps, `-an` |
| `main` / `4.0` / `1080p` / `30` | เหมือนบน แต่ `-profile:v main` (ไฟล์ใหญ่ขึ้นเล็กน้อย) |
| `baseline` เท่านั้น | `-profile:v baseline` — ไฟล์ใหญ่ขึ้นชัดเจน แต่ปลอดภัย |
| HEVC รองรับ | เพิ่มทางเลือก `libx265` สำหรับคลิปยาว ประหยัด storage ~40% |
| ทุกช่องเป็น `unknown` | ใช้ค่า conservative: `high@4.0`, 1080p30, H.264, ตัดเสียง |
| **`mov_supported: yes`** | **เลิกทำระบบแปลงไฟล์ทั้งหมด** เปิดให้อัป `.mov` ได้ตรงๆ — ประหยัดงานฝั่งเราหลายสัปดาห์ |
| `mov_supported: no` | ต้องเขียนระบบแปลงกล่อง `.mov` → `.mp4` ก่อนส่งเข้าคิวจอ |

**ต่อให้ตอบว่า `unknown` ทั้งหมด เราก็เดินงานต่อได้** — แค่จะได้ไฟล์ที่ใหญ่กว่าที่ควรและอาจเสียคุณภาพโดยไม่จำเป็น ยิ่งตอบละเอียด ผลยิ่งดี

**ถ้าจะตอบได้แค่ 2 ข้อ ขอ Q6 กับ Q1**

- **Q6 (`.mov`)** — คุ้มที่สุด เพราะถ้าตอบว่า "ได้" งานฝั่งเราหายไปเกือบทั้งหมด ไม่มีคำถามข้ออื่นที่ให้ผลตอบแทนเท่านี้
- **Q1 (profile/level)** — เสี่ยงที่สุด เพราะตอบผิดแล้ว**จอเล่นไม่ออกเลย** ส่วนข้ออื่นตอบผิดแค่ทำให้ไฟล์ใหญ่เกินจำเป็นหรือภาพแตก ไม่ถึงกับพัง

## ถ้ามีคำถามกลับ

ถามได้เลย โดยเฉพาะถ้า:

- มีจอหลายรุ่นที่ spec ต่างกันมาก จนคิดว่าควรทำไฟล์หลาย version
- firmware มีข้อจำกัดเรื่องขนาดไฟล์ หรือความยาวคลิปที่เราควรรู้
- มีฟอร์แมตที่จอ**เล่นได้ดีกว่า** mp4 ที่เราไม่รู้
