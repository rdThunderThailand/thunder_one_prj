# Player verification checklist — ตรวจ firmware กับสัญญาใหม่ของ `media_job_poll`

**สำหรับ:** ทีมที่ทำ firmware ของจอ
**เอกสารคู่กัน:** `player_contract_timeline.md` (สัญญาเต็ม) — อ่านอันนั้นก่อนถ้ายังไม่เคยอ่าน
**อัปเดตล่าสุด:** 2026-08-11

---

## มีอะไรเปลี่ยนบ้าง (สรุปให้ก่อน)

ฝั่ง server เพิ่ม 3 ฟิลด์เข้า response ของ `POST /api/core/v1/media/player/jobs` ไปแล้ว **ทั้งหมดขึ้น production แล้ว** ยิงได้เลยตอนนี้

| ฟิลด์ | อยู่ตรงไหน | จอต้องทำอะไร |
|---|---|---|
| `next_poll_after_seconds` | ระดับบนสุด | **เลิกใช้ค่าคงที่ 60 วิ** เปลี่ยนไปอ่านค่านี้แทน |
| `starts_at` | ในทุก slot | ไม่ต้องทำอะไร (ข้อมูลประกอบ) |
| `ends_at` | ในทุก slot | หยุดเล่น slot นั้นเองเมื่อนาฬิกาจอผ่านเวลานี้ ไม่ต้องรอ poll |

ทั้งสามฟิลด์เป็นการ**เพิ่มอย่างเดียว** ฟิลด์เดิมไม่ถูกแตะเลย → **firmware ตัวเดิมที่ยังไม่อัปเดตจะยังทำงานได้ปกติ ไม่พัง** แค่จะยังไม่ได้ประโยชน์จากของใหม่

---

## เตรียมก่อนเริ่ม

ต้องมี **device token** ของจอทดสอบ (ขึ้นต้นด้วย `dtk_`) ขอจากฝั่ง backend ถ้ายังไม่มี

```bash
export TOKEN="dtk_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"
export BASE="https://thundercore.vercel.app"
```

> ถ้าเทสกับ backend ที่รันในเครื่องให้เปลี่ยนเป็น `export BASE="http://localhost:3000"`

ยิงดูก่อนว่าต่อได้:

```bash
curl -sS -X POST "$BASE/api/core/v1/media/player/jobs" -H "Authorization: Bearer $TOKEN" | jq .
```

ควรได้ `{"success": true, "data": {...}}` ถ้าได้ 401 = token ผิดหรือถูก revoke

---

## T1 — `next_poll_after_seconds` มาจริงและอยู่ในช่วงที่ถูกต้อง

**ทำ:** ยิง 5 ครั้งติดกัน ดูค่าที่ได้

```bash
for i in 1 2 3 4 5; do
  curl -sS -X POST "$BASE/api/core/v1/media/player/jobs" \
    -H "Authorization: Bearer $TOKEN" | jq -r '.data.next_poll_after_seconds'
done
```

**คาดหวัง:** ได้ตัวเลข 5 ตัว **แต่ละตัวอยู่ระหว่าง 55–65** และ**ไม่เท่ากันทุกตัว** (เป็นค่าสุ่มโดยตั้งใจ เพื่อไม่ให้จอทั้งฟลีต poll พร้อมกันหลังไฟดับ)

**ถ้าได้ `null` หรือไม่มีฟิลด์นี้เลย** = คุณกำลังยิงไป backend เวอร์ชันเก่า แจ้งฝั่ง backend

---

## T2 — firmware อ่านค่านี้ไปใช้จริงหรือยัง ⬅ ข้อสำคัญที่สุด

นี่คือข้อที่เราอยากรู้คำตอบมากที่สุด เพราะ server ส่งค่าไปแล้วแต่**ถ้าจอไม่อ่าน ก็ไม่เกิดอะไรขึ้นเลย**

**ทำ:** เปิด log ของจอ แล้วปล่อยให้ poll ติดกัน 5 รอบ จับเวลาห่างระหว่างแต่ละรอบ

**คาดหวัง:** ระยะห่างแต่ละรอบ**ไม่เท่ากันเป๊ะ** และตรงกับค่า `next_poll_after_seconds` ที่ได้จากรอบก่อนหน้า

| สิ่งที่เห็นใน log | แปลว่า |
|---|---|
| ห่างกัน 60.0 วิ เป๊ะทุกรอบ | ❌ ยังใช้ค่าคงที่เดิม **ยังไม่ได้อ่านฟิลด์ใหม่** |
| ห่างกัน 57, 62, 55, 64 วิ (ไม่ซ้ำ) | ✅ อ่านแล้ว ทำงานถูกต้อง |

**ถ้ายังเป็นแบบแรก** → นี่คือสิ่งที่ต้องแก้ ดูวิธีทำที่ท้ายเอกสาร

---

## T3 — จอทนได้เมื่อฟิลด์หายไปหรือค่าประหลาด

ค่าในฟิลด์นี้จะแม่นขึ้นในอนาคต (ตอนนี้เป็นค่าสุ่ม ต่อไปจะคำนวณจากขอบเวลาจริง) แปลว่า**ค่าจะเปลี่ยนช่วงได้** จอต้องไม่พัง

**ทำ:** ทดสอบด้วยการ mock response ฝั่งจอ (ไม่ต้องยิง server จริง) 3 กรณี

| กรณี | จอต้องทำ |
|---|---|
| ไม่มีฟิลด์ `next_poll_after_seconds` เลย | ใช้ค่าตั้งต้น 60 วิ ไม่ crash |
| ค่าเป็น `5` (ต่ำกว่าที่เคยเห็น) | poll หลัง 5 วิ ไม่ปัดทิ้ง |
| ค่าเป็น `600` (สูงกว่าที่เคยเห็น) | poll หลัง 600 วิ ไม่ปัดทิ้ง |

> เหตุผล: server จะ clamp ค่าไว้ที่ 5–60 ในอนาคต จอไม่ต้อง clamp ซ้ำ แค่ทำตามที่ได้รับ

---

## T4 — จอข้ามฟิลด์ที่ไม่รู้จักได้ (สำคัญต่ออนาคต)

payload นี้จะมีฟิลด์ใหม่เพิ่มอีกเรื่อยๆ (เช่นตอนรองรับจอหลายโซน) **ถ้าจอ crash ตอนเจอคีย์แปลก เราจะเพิ่มอะไรไม่ได้เลยโดยไม่ไล่อัปเดตจอทุกตัว**

**ทำ:** mock response ที่มีคีย์ปลอมแทรกเข้าไป ทั้งระดับบนสุดและใน slot

```json
{
  "device_id": "...",
  "loop_duration_seconds": 45,
  "next_poll_after_seconds": 58,
  "some_future_field": { "anything": [1, 2, 3] },
  "slots": [
    { "start_offset_seconds": 0, "duration_seconds": 15, "kind": "video",
      "another_future_field": "hello", "file": { "...": "..." } }
  ]
}
```

**คาดหวัง:** จอเล่นตามปกติ เมินคีย์ที่ไม่รู้จัก **ไม่ error ไม่ปฏิเสธทั้ง payload**

---

## T5 — `ends_at` ทำให้จอหยุดเองได้ตอนเน็ตขาด

**ทำ:**
1. mock response ที่มี slot เดียว `ends_at` = อีก 2 นาทีข้างหน้า
2. ตัดเน็ตจอ (หรือ block ไม่ให้ poll ได้)
3. รอให้เลยเวลา `ends_at`

**คาดหวัง:** จอ**หยุดเล่น slot นั้นเอง**เมื่อนาฬิกาตัวเองผ่าน `ends_at` ทั้งที่ poll ไม่ได้

**ถ้าจอยังเล่นต่อไปเรื่อยๆ** = ยังไม่ได้ใช้ `ends_at` → publication จะเล่นเกินเวลาที่ขายไว้ตอนเน็ตมีปัญหา

> `ends_at` เป็น `null` ได้ = ไม่มีวันหมดอายุ ต้องไม่ทำให้จอ crash

---

## T6 — slot ที่หายไปต้องหยุดเล่นทันที (กลไกเดิม ตรวจว่ายังไม่พัง)

ข้อนี้เป็นพฤติกรรมเดิมที่มีอยู่แล้ว ตรวจว่าการเพิ่มฟิลด์ใหม่ไม่ทำให้เสีย

**ทำ:** mock 2 response ติดกัน — รอบแรกมี 3 slot รอบสองเหลือ 2 slot (เอาตัวกลางออก)

**คาดหวัง:** จอเลิกเล่นตัวที่หายไปทันที **ไม่ต้องรอคำสั่ง "หยุด"** — ระบบนี้ไม่มี job ชนิด revoke แต่ละ poll คือ state ล่าสุดทั้งหมด ไม่ใช่ diff

| # | หัวข้อ | ผล | หมายเหตุ |
|---|---|---|---|
| T1 | `next_poll_after_seconds` มาจริง อยู่ในช่วง 55–65 และไม่ซ้ำ | ☐ ผ่าน ☐ ไม่ผ่าน | |
| T2 | **firmware อ่านค่านี้ไปใช้จริง (ไม่ใช่ 60 วิเป๊ะ)** | ☐ ผ่าน ☐ ไม่ผ่าน | ⬅ สำคัญสุด |
| T3 | ทนได้เมื่อฟิลด์หาย / ค่าต่ำ / ค่าสูง | ☐ ผ่าน ☐ ไม่ผ่าน | |
| T4 | ข้ามฟิลด์ที่ไม่รู้จักได้ ไม่ crash | ☐ ผ่าน ☐ ไม่ผ่าน | |

**คำถามที่อยากได้คำตอบพร้อมตาราง:**
1. ตอนนี้ firmware ตั้ง poll ไว้ทุกกี่วินาที และเป็นค่า hardcode หรืออ่านจาก config?
2. ถ้า T2 ไม่ผ่าน — แก้ให้อ่านจาก response ได้ภายในเมื่อไหร่?
3. จอทดสอบตัวนี้อยู่บนโต๊ะหรือติดตั้งหน้างานจริงแล้ว?

> ข้อ 3 สำคัญเพราะถ้ายังเป็นเครื่องเทส เรายังเพิ่มฟิลด์ในสัญญาได้อิสระ พอลงจอจริงแล้วการเพิ่มฟิลด์จะแพงขึ้นมาก

## วิธีแก้ถ้า T2 ไม่ผ่าน

โค้ดเดิมส่วนใหญ่จะประมาณนี้:

```
POLL_INTERVAL = 60
loop {
    response = poll()
    handle(response)
    sleep(POLL_INTERVAL)
}
```

เปลี่ยนเป็น:

```
DEFAULT_POLL_INTERVAL = 60      // ใช้เฉพาะก่อนได้ response แรก และตอนฟิลด์หาย
nextInterval = DEFAULT_POLL_INTERVAL

loop {
    response = poll()
    handle(response)

    // อ่านค่าจาก server ถ้าไม่มีให้ใช้ค่าเดิม
    nextInterval = response.next_poll_after_seconds ?? DEFAULT_POLL_INTERVAL

    sleep(nextInterval)
}
```

**ข้อควรระวัง 3 ข้อ:**

1. **เป็นระยะเวลา ไม่ใช่เวลานาฬิกา** — `58` แปลว่า "อีก 58 วินาที" ไม่ใช่ "ตอน 58 นาที" ตั้งใจออกแบบแบบนี้เพื่อให้นาฬิกาจอเพี้ยนแล้วไม่พัง อย่าแปลงเป็น timestamp
2. **อ่านใหม่ทุกรอบ** — อย่าอ่านครั้งเดียวตอนบูตแล้วจำไว้ตลอด ค่าจะเปลี่ยนทุก response และในอนาคตจะเปลี่ยนตามสถานการณ์จริง
3. **poll ล้มเหลวให้ใช้ค่าล่าสุดที่ได้** (หรือค่าตั้งต้น) แล้ว retry อย่าวน retry รัวๆ
